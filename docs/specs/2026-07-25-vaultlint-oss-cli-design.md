# vaultlint OSS CLI — дизайн MVP

Дата: 2026-07-25
Обновлено: 2026-07-26 — см. «Ревизия 2026-07-26: разворот VL004 и пересборка VL001» и
«Пересборка VL001: замер, сужение, двухфазный скан»
Статус: реализовано до v0.1.0, публикация на crates.io остановлена до устранения блокеров ревизии

## Что строим

Бесплатный open-source CLI `vaultlint`: статический анализатор Solana-программ на Rust/Anchor,
который ловит пять классов уязвимостей детерминированными правилами, без LLM и без сетевых вызовов.

Это линтер, а не прувер. Он находит паттерны, скоррелированные с уязвимостями, и не доказывает
отсутствие багов. Цель MVP — высокая точность на узком наборе правил, а не полнота.

Роль в бизнесе: верх воронки и доказательство компетенции для платного hosted-продукта
(LLM-анализ, GitHub-приложение, дашборд). Граница open core: всё, что бесплатно в эксплуатации,
остаётся в OSS; всё, что стоит денег за вызов или даёт хостинг-удобство, уходит в платное.

## Цели и не-цели

Цели:
- Пять правил с низким уровнем ложных срабатываний.
- Работа офлайн, установка одной командой, вывод в терминал / JSON / SARIF.
- Репозиторий, оформленный так, чтобы им можно было пользоваться и в него можно было контрибьютить.

Не-цели MVP:
- LLM-слой любого вида.
- Межфункциональный и межмодульный dataflow-анализ.
- Резолв типов между файлами (`syn` даёт синтаксис, не семантику).
- Конфигурационный файл проекта — подавление находок делается комментариями в коде.
- GitHub Action — отдельный репозиторий и отдельная спека после v0.1.0.

## Размещение и публикация

- GitHub-организация `vaultlint`, репозиторий `vaultlint/vaultlint`, публичный с первого коммита.
- Локально — папка `code/` внутри проекта `vaultlint.com`, отдельный независимый git-репозиторий.
- Имя `vaultlint` свободно на crates.io (проверено 2026-07-25) и как GitHub-организация.
- Лицензия: MIT OR Apache-2.0 (двойная, как принято в Rust-экосистеме).
- Публикация вертикальными срезами: каждый срез — рабочее состояние, свой коммит и пуш.

## Архитектура

Один крейт `vaultlint`, экспортирующий и библиотеку (`lib.rs`), и бинарник (`main.rs`).
Разделение на воркспейс `core` + `cli` отложено до появления облачного слоя.

```
code/
  Cargo.toml
  README.md  LICENSE-MIT  LICENSE-APACHE
  src/
    main.rs           # clap: vaultlint scan <path> [--format] [--fail-on]
    lib.rs
    scan.rs           # walkdir по *.rs, пропуск target/ и скрытых каталогов
    parse.rs          # syn::parse_file, позиции узлов -> строка/колонка
    anchor/           # модель Anchor: Accounts-структуры, поля, констрейнты
    rules/            # по файлу на правило + реестр
    finding.rs
    report/           # human.rs, json.rs, sarif.rs
  examples/
    vulnerable/       # по одной уязвимой программе на правило
    clean/            # корректная программа-канарейка: ноль находок
  tests/              # интеграционные прогоны по examples/
  .github/workflows/ci.yml
```

Поток данных: путь -> обход файлов -> парсинг каждого файла в `syn::File` -> построение
модели Anchor -> прогон всех правил над контекстом -> фильтр подавлений -> рендер -> код выхода.

Зависимости: `syn` (парсинг, фича `full`), `proc-macro2` с фичей `span-locations`
(без неё `Span::start()` не отдаёт строку/колонку вне процедурного макроса), `walkdir`, `clap`,
`serde`/`serde_json`, `toml` (чтение `overflow-checks`), `anyhow`, `owo-colors`.

### Модель находки

```rust
#[non_exhaustive]
struct Finding {
    rule_id: Cow<'static, str>, // "VL001"
    severity: Severity,         // High | Medium | Low
    title: Cow<'static, str>,   // "unproven authority on initialization"
    message: String,            // конкретика с именем аккаунта/выражения
    file: PathBuf,
    line: usize,
    column: usize,              // best-effort
    snippet: String,            // строка исходника
    help: Cow<'static, str>,    // как чинить
    docs_url: String,           // https://vaultlint.com/rules/VL001
}
```

Поля `rule_id`, `title` и `help` — `Cow<'static, str>` вместо `&'static str`. Причина:
крейт выводит `Deserialize` для `Finding`, чтобы потребитель мог прочитать собственный JSON
vaultlint его же типами. `serde` не умеет десериализовать в `&'static str`, поскольку
десериализованное значение живёт дольше, чем любая статически известная строка. `Cow` сохраняет
нулевое размещение при внутреннем построении (`Cow::Borrowed` на строковом литерале) и допускает
`Cow::Owned` при десериализации.

`Finding`, `ScanReport`, `ScanOptions` и `SkippedFile` помечены `#[non_exhaustive]`: добавление
поля в будущих версиях не ломает semver. Следствие для `ScanOptions`: внешний код не может
строить его через struct-literal (атрибут `#[non_exhaustive]` запрещает это вне крейта), поэтому
добавлен конструктор `ScanOptions::new(root: impl Into<PathBuf>)`.

Номер строки — основной якорь находки; колонка отображается по возможности.
`docs_url` ведёт на страницу правила на сайте: правила гонят трафик на контент.

### API правила

Модуль `rules` — `pub(crate)`. `RuleContext`, `Rule` и `LinkedRule` не являются частью публичного
API крейта: возможность писать сторонние правила в 0.1.0 намеренно не поддерживается. Добавление
нового правила требует изменения самого крейта. Причина: каждый публичный элемент, вышедший в
0.1.0, — это обязательство, которое нельзя отозвать, не подняв мажорную версию. Стабилизировать
интерфейс расширения до того, как он испытан хотя бы на пяти правилах, значит заморозить
преждевременное решение.

Внутреннее устройство для справки:

```rust
// pub(crate)
struct RuleContext<'a> {
    path: &'a Path,
    source: &'a str,
    ast: &'a syn::File,
    anchor: &'a AnchorModel,
    overflow_checks: bool,
}

// pub(crate)
trait Rule {
    fn check(&self, ctx: &RuleContext<'_>, out: &mut Vec<Finding>);
}
```

Правило ничего не знает про обход файлов и форматы вывода.

`overflow_checks` — не общескановое значение, а свойство конкретного файла: сканер резолвит
для каждого файла корень его воркспейса (см. VL003) и кладёт в контекст флаг именно этого
корня. Один запуск может покрывать несколько воркспейсов с разными настройками.

### Модель Anchor

Единственное место в коде, знающее синтаксис Anchor. Строится за один проход по файлу,
тестируется отдельно от правил.

Модуль `anchor` — `pub(crate)`. Типы `AnchorModel`, `AccountsStruct`, `AccountField`,
`AccountTy` и `Constraint` не входят в публичный API: они слишком тесно связаны с форматом
атрибутов Anchor, и их форма будет меняться по мере расширения набора правил.

Внутреннее устройство для справки:

```rust
// pub(crate)
struct AnchorModel { accounts_structs: Vec<AccountsStruct> }

// pub(crate)
struct AccountsStruct {
    name: String,
    instruction_args: Vec<String>,  // имена аргументов из #[instruction(...)]
    fields: Vec<AccountField>,
}

// pub(crate)
struct AccountField {
    name: String,
    ty: AccountTy,
    constraints: Vec<Constraint>,
    span: Span,  // pub(crate), используется правилами для позиции находки
}

// pub(crate)
enum AccountTy {
    Signer, Account(String), AccountInfo, UncheckedAccount,
    Program, SystemAccount, Sysvar, Other(String)
}

// pub(crate)
enum Constraint {
    Init, Mut, Seeds(String), Bump(Option<String>),
    HasOne(String), Custom(String), Other(String, String)
}
```

Ключевое различение: `Bump(None)` — голый `bump` (пересчёт), `Bump(Some(expr))` — `bump = expr`
(валидация сохранённого канонического bump).

## Правила

Каждое правило намеренно узкое. При сомнении — не флагать.

### VL001 — unproven authority on initialization (Medium)

Правило **не** детектирует пропущенный signer-check в общем виде и не должно этого заявлять:
обобщённая формулировка была реализована, замерена и отброшена (см. «Ревизия 2026-07-26» и
«Пересборка VL001»). Ловится ровно одна форма — та, что была реальным багом в marginfi-v2.

Флагаем поле `Accounts`-структуры, для которого выполнены **все** условия:

- **T1** — тип `AccountInfo` или `UncheckedAccount` (`Box` уже развёрнут);
- **T2** — имя похоже на authority: совпадает с маркером или оканчивается на `_<маркер>`.
  Маркеры: `authority`, `admin`, `owner`, `signer`, `payer`, `delegate`, `manager`,
  `governance`. Суффиксное сравнение обязательно — в реальных программах доминируют
  `pool_authority`, `vault_authority`, `update_authority`;
- **T3** — в этой же структуре что-то создаётся через `init` / `init_if_needed`;
- **T4** — имя поля встречается целым идентификатором внутри `seeds = [...]` того самого
  создаваемого соседа. Порядок объявления решает, какой из `init`-соседей считается названным;
- **T5** — тело хендлера читает ключ поля и пишет его в состояние. Хендлер ищется по
  cross-file индексу использований (см. «Двухфазный скан»): функции, принимающие
  `Context<S>`, и методы `impl S`. Учитываются обе записи имени — `ctx.accounts.<поле>` и
  голая, после `let <поле> = &ctx.accounts.<поле>` или деструктуризации `ctx.accounts`.

Молчим (любое из условий достаточно):

- **S1** — собственный `#[account(...)]` поля уже его закрепляет: `signer`, `address = ...`,
  `constraint = ...`, `seeds`;
- **S2** — сосед, который **не** создаётся этой инструкцией, привязывает поле через
  `has_one = <имя>` или `constraint`, в том числе в форме с указанием пространства имён;
- **S3** — в структуре есть authority-именованный `Signer`, чья связь с полем установлена;
- **S4** — использование поля доказывает подпись: прямая проверка `is_signer` либо передача
  поля в вызов на один уровень вглубь, где проверка происходит. T5 и S4 обязаны видеть
  **один и тот же** набор написаний имени: если T5 научится голой форме, а S4 — нет, каждый
  корректный `is_signer` на деструктурированном локале превратится в ложное срабатывание.
  Это свойство закреплено парными тестами, убиваемыми непересекающимися мутациями.

**`/// CHECK:` не является сигналом.** Anchor требует этот doc-комментарий над каждым
`AccountInfo`/`UncheckedAccount` — без него программа не компилируется. Он стоит и над
проверенными, и над непроверенными полями, поэтому не различает их и не используется правилом
ни как повод флагнуть, ни как повод промолчать.

Фикс в сообщении: объявить поле как `Signer<'info>`, либо привязать его к аккаунту, чья
authority уже доказана (`has_one = ...`, `constraint = ...`). Если permissionless — это
намерение, находку следует заглушить.

Severity — **Medium**, а не High: находка означает «подтвердите намерение», а не «у вас дыра».
Permissionless-by-design без знания протокола неотличим от бага.

Осознанные пропуски, которые обязаны быть заявлены в README и на странице правила: тела
хендлеров читаются на один вызов вглубь, поэтому программа, проверяющая `is_signer` дальше,
будет отмечена; поле, переданное через `remaining_accounts`, невидимо; рассматриваются только
authority-именованные поля.

### VL002 — missing owner check (High)

Единственное правило severity High: только оно поднимает ненулевой код выхода при дефолтном
`--fail-on high`. Поэтому его ложное срабатывание — это чей-то красный CI, и цена ошибки здесь
выше, чем у остальных четырёх.

Правило флагает **ручную десериализацию сырых данных аккаунта** — `T::try_from_slice(...)` или
другой свободный вызов `deserialize` поверх байтов аккаунта — в функции, где ничто не доказывает,
какой программе этот аккаунт принадлежит.

**Условие срабатывания:**

- **T1** — среди аргументов вызова-десериализатора есть сырое чтение данных. Сигналы:
  `.data.borrow()`, `.data.borrow_mut()`, `.try_borrow_data()`, `.try_borrow_mut_data()` — либо
  прямо в аргументе (`T::try_from_slice(&x.data.borrow())`), либо через **один шаг** промежуточной
  локальной переменной: `let d = acc.try_borrow_data()?;` и далее `T::try_from_slice(&d[8..])`.
  Вторая форма в реальном коде доминирует. Строка находки — вызов десериализатора, не `let`.
  Локальные `let` собираются и во вложенных блоках.

**Глушители:**

- **S1** — в теле есть именно **проверка** владельца, а не упоминание. Три позиции проверки:
  бинарное `==`/`!=`, в одном из операндов которого есть `.owner`; макрос из `OWNER_CHECK_MACROS`
  (`require_keys_eq`, `require_keys_neq`, `require_eq`, `require_neq`, `require`, `assert_eq`,
  `assert_ne`), в токенах которого есть `.owner`; вызов, чей последний сегмент пути в нижнем
  регистре содержит `owner` или `owned` — это покрывает распространённую форму-хелпер
  `assert_owned_by(account, &crate::ID)?`, `check_account_owner`, `is_owned_by`. Сегмент, а не
  весь текст выражения: аргумент с именем `owner` глушителем быть не должен.
- **S2** — **проверка адреса и есть проверка владельца.** Подписать за свой PDA может только сама
  программа, поэтому аккаунт с данными по адресу, выведенному из seeds и **id этой программы**,
  создан этой программой и ей же принадлежит. Глушим, когда выполнены оба условия: (а) в теле есть
  вызов с последним сегментом `find_program_address`, `create_program_address` или
  `assert_derivation`; (б) ресивер сырого чтения встречается **целым идентификатором** в тексте
  какого-нибудь сравнения `==`/`!=`, или макроса из `OWNER_CHECK_MACROS`, или среди аргументов
  самого вызова вывода адреса. Условие (б) обязательно: без него вывод PDA для аккаунта X глушил бы
  сырое чтение постороннего аккаунта Y — ловушка «проверили что-то, значит проверили всё».
- **S3** — то же самое, но доказательство лежит в структуре, а не в теле: у поля, которое читается,
  стоит Anchor-ограничение `seeds = [...]` или `address = ...`. Anchor проверяет их **до** входа в
  тело хендлера. Ищем через `Context<S>` вызывающей функции: `S` находится среди `Accounts`-структур
  файла, поле берётся из ресивера вида `ctx.accounts.<поле>`. Совпадение — по квалифицированному
  пути и точному имени поля: глушит только то поле, которое действительно читают.

Ресивер для S2 и для S3 извлекается по-разному, и это намеренно. S3 нужна **квалифицированная**
форма (`ctx.accounts.proposal` → поле `proposal`), S2 — **последний** сегмент-идентификатор пути,
пропуская сегменты-вызовы: `ctx.accounts.collection_metadata` → `collection_metadata`,
`source_account.to_account_info()` → `source_account`. Если брать для S2 ведущий идентификатор, то
для любого Anchor-чтения это `ctx`, условие (б) вырождается в «в теле есть хоть какое-то сравнение
со словом ctx» и правило глушится проверкой **другого** аккаунта. Это была реальная ошибка,
поймавшая настоящую находку; закрыта тестом.

Сравнение внутри макроса тоже считается доказательством: токены макроса никогда не разбираются в
`Expr::Binary`, поэтому `assert!(pda == account.key)` иначе не виден вовсе. Засчитываются токены
**с `==` или `!=`**, а не любой макрос: `msg!("{}", account.key)` называет аккаунт и не доказывает
ничего, и допуск любого макроса сделал бы `msg!` глушителем. Тоже закрыто тестом.

Порядок не требуется: проверка после чтения всё равно останавливает программу до действий над
плохими данными, а требование порядка потребовало бы тащить в правило позиции. Осознанное
следствие: код, который десериализует на строке 49 и сверяет адрес на 65–69, молчит.

Не флагаем типизированные `Account<'info, T>` — Anchor сам проверяет владельца и дискриминатор.
Метод-форма `account.try_deserialize(&mut data)` намеренно **не** распознаётся: это и есть
**безопасный** путь Anchor, ровно то, что `Account<'info, T>` делает внутри уже после проверки
владельца. Добавить её значило бы флагать правильный код.

Само по себе чтение `.owner` проверкой не считается. В Solana `.owner` означает две разные вещи:
`AccountInfo::owner` — программу-владельца, о которой правило, — и поле `owner` у
SPL-token-аккаунта, то есть кошелёк-держатель токенов; второе в прикладном коде встречается чаще.
Трактовка любого упоминания `.owner` как проверки глушила правило почти везде.

Фикс: использовать `Account<'info, T>` либо явную проверку `require_keys_eq!(*acc.owner, crate::ID)`.

### VL003 — overflow-checks не включён (Medium; арифметические места — Low)

Правило перевёрнуто относительно первоначального замысла. Оно больше не сыплет находкой на
каждую арифметическую операцию — оно один раз задаёт вопрос о профиле сборки.

**Почему.** При `[profile.release] overflow-checks = true` переполнение паникует: транзакция
откатывается, средства не двигаются. Solana-программы собираются в release-режиме, поэтому одна
строка в одном манифесте выключает весь класс «молча обернулось». Это и есть единственное
действие, о котором имеет смысл говорить.

**Замер, на котором основано решение.** На корпусе из двенадцати production-репозиториев
пооперационная форма правила давала **382 находки, из них ноль пригодных к действию**: 370 были
Low, потому что проект уже ставил флаг, а все 12 Medium — это один защищённый инвариантом
счётчик `u8` в drift (`open_orders += 1 / -= 1`). Правило, у которого на двенадцати кодовых базах
нет ни одной содержательной находки, — это не задача тюнинга, а продуктовый вопрос.

**Поведение.**

1. Воркспейс ставит `overflow-checks = true` → VL003 молчит полностью: ни проектной находки, ни
   пооперационных.
2. Не ставит → одна находка **Medium** на корень воркспейса (`overflow-checks is not enabled`,
   привязана к строке `[profile.release]` в корневом манифесте, иначе к строке 1), плюс все
   арифметические места под этим корнем на уровне **Low** — как свидетельство того, что именно
   обернётся. Проектная находка появляется только если под этим корнем осталось хотя бы одно
   неподавленное арифметическое место: воркспейс без арифметики вопроса не получает, а подавление
   всех мест комментарием `// vaultlint:allow VL003` гасит и проектную находку.
3. Над файлом вообще нет `Cargo.toml` → пооперационные находки выдаются, проектная нет: назвать
   файл, который надо отредактировать, нечем, а совет отредактировать несуществующий файл
   бесполезен.

Результат на том же корпусе: **382 → 26** (3 проектных Medium + 23 Low) на 24 различных корнях
воркспейсов, 22 из которых молчат. Одна из трёх проектных находок — настоящая: drift
(protocol-v2) действительно собирает свою on-chain программу без `overflow-checks`.

**Какой манифест считается.** Cargo игнорирует `[profile.*]` в любом манифесте, кроме корня
воркспейса. Поэтому «ближайший манифест побеждает» — тоже неверное разрешение: линтер похвалил бы
за строку, которая ни на что не влияет. Корень ищется так же, как это делает Cargo:

- ближайший вверх по дереву манифест — это манифест пакета;
- если у него есть `package.workspace = "<путь>"` и по этому пути лежит `Cargo.toml` — это корень;
- иначе первый предок с таблицей `[workspace]`; если его `workspace.exclude` покрывает каталог
  пакета, пакет сам себе корень (вложенные воркспейсы Cargo запрещает, поэтому кандидат ровно
  один);
- если предка с `[workspace]` нет, корень — сам манифест пакета.

Глоб-маски `workspace.members` не разбираются: манифест, объявляющий `[workspace]` и не
перечисляющий лежащий под ним пакет, ломает сборку самого Cargo, так что на любом собирающемся
проекте «ближайший предок с `[workspace]` минус `exclude`» — правильный ответ.

Пути разрешаются на абсолютном лексически нормализованном виде (`std::path::absolute` плюс
схлопывание `..` без обращения к файловой системе; `canonicalize` не используется — он ходит на
диск и разворачивает симлинки). Без этого два написания одного и того же корня давали два ключа
и, следовательно, две проектные находки, а относительный корень скана не мог увидеть корень
воркспейса выше текущего каталога процесса и называл манифест пакета — ровно ту ошибку, ради
устранения которой правило и переписывалось. Отчётный путь при этом остаётся относительным, если
относительным был корень скана.

**Что считается арифметическим местом.** Бинарная арифметика `+`, `-`, `*` и составные
присваивания `+=`, `-=`, `*=`, результат которых пишется в поле структуры. Правило не проверяет,
что это именно состояние аккаунта, поэтому и в сообщении говорится «в поле структуры», а не «в
состояние аккаунта». Локальные переменные и константы не флагаются. Гейт `#[cfg(test)]`
разбирается общим распознавателем `scope::attrs_have_cfg_test` (см. раздел про отбор файлов), а не
поиском подстроки: `#[cfg(feature = "test")]` — это код, который уезжает в сборку при включённой
фиче, и глушить его нельзя.

Не реализовано намеренно: сужение цели присваивания до настоящего состояния аккаунта и форма с
промежуточной локальной переменной (`let new = v.balance - amount; v.balance = new;`). После
инверсии пооперационных находок на всём корпусе остаётся 23 штуки, и точность в них ничего не
покупает.

Фикс: `overflow-checks = true` в корневом манифесте, либо `checked_sub` / `checked_add` /
`checked_mul` с обработкой `None`.

### VL004 — non-canonical PDA bump (Medium)

Флагаем поле с констрейнтом `seeds` и `bump = <expr>`, где `<expr>` — значение, подконтрольное
вызывающему: голый идентификатор, совпадающий с именем аргумента из `#[instruction(...)]` той же
структуры. Отдельно флагаем прямые вызовы `Pubkey::create_program_address`.

Не флагаем:
- голый `bump` без `= expr` — Anchor разворачивает его в `find_program_address`, то есть сам
  вычисляет канонический bump. Это безопасная и рекомендуемая форма;
- `bump = <field>.bump` и любой другой доступ к полю аккаунта — валидация против сохранённого
  канонического bump;
- аккаунты с `init`.

Фикс: убрать `= <expr>` и оставить голый `bump`, либо валидировать против сохранённого
канонического bump (`bump = vault.bump`), где `vault.bump` был записан при `init`.

Обоснование — из кодогенерации самого Anchor
(`lang/syn/src/codegen/accounts/constraints.rs`):

```
// [list], no bump       -> find_program_address + store __bump
// [list], explicit bump -> create_program_address with list + bump
```

`find_program_address` перебирает bump от 255 вниз и возвращает первый валидный — канонический,
единственный. `create_program_address` принимает тот bump, который ему дали, включая
неканонический: для одних и тех же seeds существует несколько валидных адресов, и злоумышленник
выбирает нужный ему. Поэтому опасна именно форма с `= expr`, и только когда expr приходит извне.

### VL005 — unchecked CPI (Medium)

Правило флагает не сам факт вызова `invoke` / `invoke_signed`, а **подконтрольность
вызывающему того program id, с которым этот вызов уходит**. Arbitrary-CPI возможен только тогда,
когда `program_id` инструкции пришёл из аккаунта, переданного вызывающим. Если инструкцию
собрал SDK-билдер с зашитой константой, разработчику нечего проверять и находка неисполнима.

Имя вызова сопоставляется по **последнему сегменту пути**, поэтому `solana_program::program::invoke`
и голый `invoke` считаются одинаково.

**Условия срабатывания (нужны оба):**

- **T1** — первый аргумент разрешается в значение `Instruction`, собранное **в теле этой же
  функции**, в одной из трёх форм:
  - структурный литерал, у которого последний сегмент пути — `Instruction`, с полем `program_id`;
  - вызов `Instruction::new_with_borsh` / `new_with_bincode` / `new_with_bytes` — program id
    берётся из **первого аргумента**;
  - вызов, в пути которого есть сегмент `spl_token` или `spl_token_2022`, — эти билдеры
    принимают `token_program_id: &Pubkey` **нулевым аргументом**, то есть program id тут как раз
    подконтролен вызывающему.

  «Разрешается» — либо выражение написано прямо в месте вызова (возможно за `&`), либо это путь
  к локальному `let`, чей инициализатор — одна из этих форм (тоже возможно за `&`, с отбрасыванием
  хвостового `?`). Один уровень косвенности, не больше. Привязка выбирается **позиционно**: берётся
  последняя привязка с этим именем, расположенная в исходнике **до** вызова, — иначе перекрытие имени
  ниже по телу приписывает безопасному вызову чужое выражение.

- **T2** — выражение program id **выведено из аккаунта**: его нормализованный текст содержит
  `.key`. Это покрывает `*x.key`, `x.key()`, `*x.to_account_info().key`, `x.key().clone()`.
  Иначе id — константа или `Pubkey`, который программа задала сама, и правило молчит.

**Глушители:**

- **S1** — в теле функции есть один из сигналов сверки: `require_keys_eq!`, `::ID`, `assert_eq!(`,
  `program_id==`. Последний живой, а не мёртвый: `normalised` вырезает все пробелы, поэтому
  исходное `if program_id == expected` превращается в `program_id==expected`.
- **S2** — аккаунт объявлен как Anchor `Program<'info, T>`, чей id Anchor проверяет сам при
  десериализации. Источник объявления — три формы: параметр `Context<S>` (ищем `S` среди
  `Accounts`-структур файла), параметр, сам типизированный как `Program<'info, T>`, и параметр,
  чей тип — `Accounts`-структура, переданная без обёртки `Context` (идиома
  `deposit_logic(&mut ctx.accounts, …)`). `Box<...>` разворачивается. Совпадение ищется по
  **квалифицированному пути** (`ctx.accounts.<поле>`, `<параметр>.<поле>`) и только внутри
  ресивера выражения — иначе однoимённое поле чужой структуры глушит непроверенный `AccountInfo`.
- **S5** — у функции есть параметр типа `CpiContext<…>`. Это CPI-хелпер, а не хендлер
  инструкции: аккаунты, включая целевую программу, ему передаёт вызывающий, и проверить их он
  не может по устройству. Отвечает вызывающий хендлер, а он принимает `Context`, не `CpiContext`.
  Сравнение — точное равенство последнего сегмента; суффиксное совпадение заглушило бы **все**
  настоящие хендлеры, и это закрыто отдельным тестом.

Сообщение называет конкретное выражение: `` `*ctx.accounts.target_program.key` supplies the
program id for this CPI… ``

Фикс: типизированный CPI Anchor либо явная проверка program id перед вызовом.

Осознанные пробелы: сокращённая через `use` форма `instruction::transfer(…)` не имеет сегмента
`spl_token` и не распознаётся — пропущенная находка, приемлемое направление ошибки.
`spl_associated_token_account` намеренно **не** входит в список: его
`create_associated_token_account(funder, …)` держит нулевым аргументом плательщика, и включение
модуля выдавало бы `payer.key` за program id.

### Подавление находок

Комментарий `// vaultlint:allow VL003 — причина` на строке находки гасит её. Если его там нет,
поднимаемся вверх по строкам, пропуская **непрерывный блок комментариев и атрибутов**
(`//`, `///`, `#[...]`, пустые строки внутри блока), и ищем комментарий там. Реализуется
проверкой текста исходных строк, без изменения AST.

Подъём по блоку обязателен, а не «одна строка выше». Anchor требует `/// CHECK:` над каждым
`AccountInfo`, а `seeds` требует атрибут `#[account(...)]` — то есть для VL001 и VL004 строка
над находкой занята всегда, и правило «строка выше» делает подавление для них физически
недостижимым.

Идентификатор правила сопоставляется по границе слова, а не по подстроке: `VL0011` не должен
гасить `VL001`.

Это входит в MVP осознанно: ложное срабатывание — риск номер один, и разработчику нужен способ
заглушить одну находку, а не удалить инструмент целиком. Механизм подавления обязан работать для
каждого правила, и это покрывается тестом на каждое правило, а не на выборочные.

## Вывод и коды выхода

Человекочитаемый формат (по умолчанию) повторяет демо с лендинга:

```
$ vaultlint scan ./programs/staking
→ analyzing 14 Rust files (Anchor 0.30) …

✗ HIGH  missing owner check
        programs/staking/src/instructions/withdraw.rs:42
        Account data is deserialised without verifying the account owner.
        An attacker can pass a look-alike account owned by another program.

3 issues found · 1 high · 2 medium
```

Цвет отключается при `NO_COLOR` и когда stdout не является терминалом. Версия Anchor в шапке
берётся из версии зависимости `anchor-lang` в `Cargo.toml` проекта; если зависимость не найдена,
шапка печатается без неё.

`--format json` — объект `{ "findings": [...], "skipped": [...] }`, а не голый массив. Формат
фиксируется до 0.1.0 именно в этой форме: пропущенные файлы обязаны быть видны в машинном выводе.
CI, который не смог распарсить половину программы, должен об этом узнать, а не получить пустой
список находок.

`--format sarif` — SARIF 2.1.0; GitHub понимает его нативно и показывает находки во вкладке
Security репозитория без дополнительной интеграции. Требования к корректности и принятые решения:

- `artifactLocation.uri` реализован через `originalUriBaseIds`: ран объявляет `%SRCROOT%`,
  отображённый на абсолютный `file://`-URI корня скана (с обязательным слэшем на конце), и все
  находки внутри этого корня выходят с относительным `uri` плюс `"uriBaseId": "%SRCROOT%"`.
  Находка вне корня скана — реально случается: VL003 указывает на корневой `Cargo.toml`
  воркспейса, который может лежать *выше* переданного пути — получает абсолютный `file://`-URI без
  `uriBaseId`. Третьей опции нет: `../`-относительная ссылка — это ровно та форма, которую GitHub
  code scanning молча отбрасывает, а подавлять находку значит терять информацию; абсолютный URI
  хуже только по одному критерию, зато сохраняет находку. При нормализации путей
  `std::fs::canonicalize` запрещён во всём крейте (трогает файловую систему, разрешает симлинки);
  вместо него используется `std::path::absolute` плюс лексическое схлопывание `..`-сегментов.
  Нормализация принципиальна: относительный корень скана даёт относительные пути в находках, и
  `strip_prefix(абсолютный_корень, относительная_находка)` всегда проваливается — в первой
  реализации именно это происходило, и все URI выходили абсолютными. Юнит-тесты этого не поймали,
  потому что строили пути с абсолютными значениями; поймал только интеграционный тест,
  запускающий реальный бинарник с относительным аргументом;
- пропущенные файлы попадают в `invocations[].toolExecutionNotifications`;
- дескрипторы правил (`reportingDescriptor`) берутся из статической таблицы на `rule_id`, а не
  из первой попавшейся находки. `reportingDescriptor` описывает правило, а не один его случай.
  Это стало существенным для VL003: правило выдаёт два принципиально разных вида находок под
  одним `rule_id` — Medium на корневой манифест и Low на арифметические места — и текст
  дескриптора менялся в зависимости от того, какая находка отсортировалась первой. Конкретный
  текст каждого результата по-прежнему несёт поле `message` на уровне результата.

Коды выхода: `0` — нет находок выше порога, `1` — есть находки выше порога, `2` — ошибка
инструмента. Порог задаётся `--fail-on high|medium|low|never`, по умолчанию `high`.
Medium-находки печатаются, но чужой CI не роняют, пока их точность не подтверждена практикой.

Файлы, которые `syn` не смог распарсить, пропускаются с предупреждением; сканирование
продолжается. Причина пропуска печатается целиком по цепочке ошибок — вместе с сообщением `syn`,
а не только с внешним контекстом «parsing <path>».

Инструмент направляют на чужие репозитории, поэтому он обязан не падать: скан выполняется в
потоке с увеличенным стеком, иначе файл с ~1000 вложенных блоков роняет процесс переполнением
стека — без находки, без пропуска и с кодом выхода в виде сигнала вместо 0/1/2. Обрыв пайпа
(`vaultlint scan . | head`) завершается штатно, а не ошибкой инструмента.

## Тестирование

По TDD: тест пишется до реализации, три уровня.

1. Юнит-тесты модели Anchor — разбор типов полей и констрейнтов, отдельно от правил.
2. На каждое правило — пара тестов из инлайновых кусочков кода: уязвимый (ровно одна находка
   с ожидаемой строкой) и здоровый (ноль находок). Негативный кейс важнее позитивного.

   **Здоровый кейс обязан отличаться от уязвимого ровно той проверкой, которую он пинит.**
   Тест, чей сниппет вообще не содержит конструкции, за которую отвечает правило, проходит и
   после удаления правила целиком — то есть не проверяет ничего, при этом создавая видимость
   гарантии точности. Это самый опасный вид теста в линтере.
3. Подавление (`// vaultlint:allow`) тестируется для каждого правила, а не выборочно.
4. Интеграционный прогон бинарника по `examples/` со сверкой точного набора
   `(rule_id, файл, строка)` — целиком, отсортированным списком. Такой тест падает одинаково и
   на новой находке, и на потерянной, и на съехавшей.
5. Форматы `json` и `sarif` прогоняются через бинарник, а не только через рендереры напрямую:
   иначе ничто не пинит, что CLI действительно доносит выбранный формат.

Программа-канарейка `examples/clean/` — корректный Anchor-контракт, на котором инструмент обязан
молчать. Любое срабатывание на ней красит сборку: это защита от роста шумности правил.

Канарейка обязана **содержать конструкции, на которые правила смотрят**: `AccountInfo`-поля,
ручную десериализацию, `invoke`, PDA с seeds. Канарейка, в которой этих конструкций нет,
недостижима для правил и молчит по построению, а не по заслугам — она не поймает ни одного
ложного срабатывания.

### Замер ложных срабатываний

Перед публикацией и перед каждым релизом правило прогоняется по реальному стороннему корпусу
(`coral-xyz/anchor`, каталог `tests/`) и находки разбираются вручную. Это не тест в CI, а
обязательный шаг релиза: точность правил — единственная метрика, которая решает судьбу
инструмента, и она не выводится из юнит-тестов на собственных фикстурах. Результат замера
фиксируется в репозитории.

## Ревизия 2026-07-26: разворот VL004 и пересборка VL001

После реализации всех тринадцати срезов инструмент прогнали по стороннему корпусу
`coral-xyz/anchor` (106 файлов, 171 находка) и провели сквозное ревью. Публикацию на crates.io
остановили. Ниже — что оказалось не так и почему это правки спеки, а не кода: код точно
реализовывал то, что здесь было написано.

### VL004 был сформулирован наоборот

Первая редакция флагала голый `bump` и советовала перейти на `bump = <сохранённый bump>`.
Это ровно обратное правильному. Проверено по кодогенерации Anchor
(`lang/syn/src/codegen/accounts/constraints.rs`): голый `bump` разворачивается в
`find_program_address`, то есть Anchor сам вычисляет канонический bump — это безопасная форма.
`bump = <expr>` разворачивается в `create_program_address`, который принимает любой переданный
bump, включая неканонический.

На проверочном файле с обеими формами инструмент флагал безопасную строку, писал причину,
физически невозможную для голого `bump` («вызывающий может подставить неканонический bump»), и
проходил мимо соседней `bump = user_bump`, где bump приходит из `#[instruction]` — то есть мимо
самой уязвимости. 61 находка из 66 по VL004 на корпусе была этой ветки.

Для инструмента безопасности это дисквалифицирующая ошибка: он не просто шумел, он учил
разработчика неверной модели и предлагал сделать программу менее безопасной. Отсюда правило
«при сомнении — не флагать» дополняется вторым: **сообщение находки обязано быть проверяемым по
первоисточнику**. Формулировки правил сверяются с кодогенерацией Anchor, а не с общим ощущением.

### VL001 нельзя было чинить в исходной формулировке

Замер: 19 находок из 27 стояли под комментарием `/// CHECK:`. Очевидный фикс — «не флагать поля
с `/// CHECK:`» — не работает: Anchor **требует** этот комментарий над каждым `AccountInfo` и
`UncheckedAccount`, без него код не компилируется. Комментарий стоит и над проверенными, и над
непроверенными полями, то есть не несёт информации. Правило в исходной формулировке
(«поле с authority-именем») нечинимо — оно смотрит на признак, который есть у всех.

Плюс правило флагало три конструкции, которые являются полноценной валидацией:
`#[account(signer)]`, `#[account(address = ...)]` и поля, закрытые `has_one` у соседа. При этом
не видело `pool_authority`, `vault_authority`, `mint_authority` — доминирующее именование в
реальных программах. Оно ошибалось чаще, чем говорило, и молчало чаще, чем должно было говорить.

Отсюда инверсия: флагаем не имя, а **отсутствие валидации при подозрительном имени**. Эта
инверсия тоже была реализована, замерена и отброшена — см. «Пересборка VL001» ниже.

### Подавление не работало там, где было нужнее всего

Механизм искал комментарий на строке находки или на одной строке выше. Но для VL001 строка выше
занята обязательным `/// CHECK:`, а для VL004 — атрибутом `#[account(...)]`. То есть для двух
самых шумных правил единственный способ заглушить ложное срабатывание был недоступен физически.
Защита от риска номер один не работала ровно в тех местах, ради которых существовала.

### Вывод для процесса

Все три дефекта родились в спеке и пережили тринадцать ревью задач, потому что каждое ревью
сверяло код с заданием, а задание было неверным. Поймал их только замер на стороннем корпусе.
Поэтому замер ложных срабатываний (см. «Тестирование») переведён из необязательного шага в
обязательный релизный гейт.

## Пересборка VL001: замер, сужение, двухфазный скан

Инвертированную формулировку («authority-имя и полное отсутствие валидации») прогнали по пяти
аудированным продакшн-программам: **26 находок, 0 истинных срабатываний, 88% ложных**. Хуже
того, правило молчало на единственном подтверждённом реальном баге — marginfi-v2, коммит
`95a4c26` *«Authority must now sign to init account as PDA»*, весь диф которого
`pub authority: UncheckedAccount<'info>` → `pub authority: Signer<'info>`.

Диагноз: причина не в порогах и не в маркерах. Каждый дискриминатор, достаточно широкий, чтобы
достать хрестоматийный случай (непроверенная authority без `init` и без seeds), неизбежно
попадает и в permissionless-by-design краны, в назначение делегатов и в CPI-форварды. Без знания
протокола эти формы неотличимы. Обобщённое правило нечинимо не в реализации, а по постановке.

Решение — сузить до формы реального бага и переименовать: **unproven authority on
initialization**. Триггеры T1–T5 и глушители S1–S4 описаны в разделе VL001. Ключевое: находка
требует связки «непроверенное поле → его ключ в `seeds` создаваемого соседа → хендлер пишет этот
ключ в созданный аккаунт».

### Двухфазный скан и индекс использований

Условие T5 требует тела хендлера, а оно живёт в другом файле, чем `Accounts`-структура. Поэтому
скан разделён на две фазы. Фаза 1 парсит каждый файл, гоняет обычные `Rule` (VL002–VL005),
собирает `FileFacts` (функции, их `Context<S>`-параметр, `impl Self` тип, имена параметров) и
**выбрасывает AST**. Фаза 2 перепарсивает только файлы, объявляющие `Accounts`-структуры, и
гоняет `LinkedRule` (VL001) поверх индекса. Тела хендлеров достаются лениво, через кэш
перепарсивания, и адресуются порядковым номером функции, а не спаном.

Два решения в индексе, каждое найдено замером и обязательно к сохранению:

- **Скоуп по крейту.** Идентификатор крейта — ближайший предок-каталог с `Cargo.toml`. Без
  этого в `sealevel-attacks` функция `LogMessage` существует и в `insecure`, и в `secure`
  крейте: проверка `is_signer` из безопасного крейта глушит находку в небезопасном. Это
  разрушает корректность, а не просто шумит.
- **Делегация по имени не нужна.** Третий проход, резолвивший вызовы по голому имени функции,
  был удалён: в канонической раскладке Anchor `instructions/deposit.rs` и
  `instructions/withdraw.rs` оба экспортируют `pub fn handler`, и проход путал их. Он к тому же
  избыточен — передать целый `ctx: Context<S>` можно только в функцию, принимающую `Context<S>`,
  а такие уже находит первый проход по имени структуры. Проверено: 158 из 354 запросов
  форвардили целый ctx, 241 кандидат, **0 новых попаданий**.

## Пересборка VL005: замер и сужение

VL005 в исходной формулировке давал **324 находки** на двенадцати деревьях, и они были
одного покроя: правило флагало всякий `invoke` в функции, в тексте которой не нашлось сигнала
сверки. Это ровно та же ошибка, что была в VL001 и VL004 — сигнал присутствует и в здоровом,
и в больном коде. Обе «эталонные» находки в теле замера оказались вызовами
`solana_system_interface::instruction::create_account(…)` и собственного типизированного
CPI-хелпера Anchor, то есть неисполнимыми.

Правило переписано так, чтобы флагать опасную вещь, а не её окрестность: подконтрольный
вызывающему program id (T1 + T2 выше). Ход замера — четыре итерации, каждая исправляла
конкретный класс ложных срабатываний, найденный ручным просмотром выживших:

| итерация | всего | что изменилось |
|---|---|---|
| исходное правило | 324 | флагался всякий `invoke` без сигнала сверки |
| T1 + T2 | 8 | **слишком мало** — вместе с шумом исчез целый класс истинных находок |
| + `spl_token` как билдер с program id нулевым аргументом | 53 | истинные находки вернулись |
| + S2b, S2c, S5 | 21 | ушли SPL-обёртки Anchor и `Program`-типизированные параметры |

Провал на втором шаге — самое ценное, что дал этот замер, и он был ошибкой **спеки**, а не
реализации. Предполагалось, что «инструкцию собрал SDK-билдер» ⇒ «program id зашит константой».
Для семейства `spl_token::instruction::*` это неверно: оно принимает `token_program_id`
**нулевым аргументом**, и передача туда непроверенного аккаунта — это буквально учебный пример
`arbitrary-cpi` из Sealevel, то есть самый известный представитель того класса, ради которого
VL005 и существует. На третьей итерации подтвердились подавленные истинные находки в
`candy-machine/program/src/utils.rs:97` и `auction-house/program/src/utils.rs:285,447`.

## Пересборка VL002: замер, отзыв и точность

Зеркало VL005. Там правило кричало на 324 местах, здесь — молчало почти везде: на тех же
двенадцати деревьях VL002 давало **8 находок**, из них 7 в учебном `program-examples`. Правило
не ошибалось, оно было практически инертно, и это хуже, потому что VL002 — единственное High.

Две причины, обе в `src/rules/owner.rs`.

**Глушитель считал проверкой любое упоминание `.owner`.** Код был `if normalised(block)
.contains(".owner") { return; }` с комментарием «намеренно щедро: пропущенная находка дешевле
ложной». Инстинкт был верный, механизм — нет. `.owner` в Solana означает две несвязанные вещи:
`AccountInfo::owner` (программа-владелец) и поле `owner` десериализованного SPL-token-аккаунта
(кошелёк-держатель), и второе в прикладном коде встречается заметно чаще. Одна строка
`let holder = token_account.owner;` — и правило молчало на всю функцию.

**Распознавалась ровно одна форма сырого чтения** — `.data.borrow()`, написанная прямо в
аргументе. В корпусе `try_borrow_data` встречается в 59 файлах, `try_borrow_mut_data` в 55,
`data.borrow_mut()` в 58 — сопоставимо с 65 у `data.borrow()`, и ни одна не была видна. Хуже
того, доминирующая реальная форма вообще не inline: `let data = acc.try_borrow_data()?;`
и десериализация уже из `data`.

Дальше — три итерации, отзыв и два круга точности:

| итерация | всего | что изменилось |
|---|---|---|
| исходное правило | 8 | глушило любое `.owner`, видело одну форму чтения |
| проверка вместо упоминания + четыре сигнала чтения + шаг через `let` | 44 | отзыв восстановлен |
| + S2 (вывод PDA) и S3 (Anchor-ограничения `seeds`/`address`) | 32 | ушёл класс «адрес проверен» |
| + последний сегмент ресивера, сравнение внутри `assert!` | 31 | вернулась истинная находка, ушли две ложные |

Второй круг точности стоит записать целиком, потому что это снова была ошибка **спеки**.
Условие (б) глушителя S2 требует, чтобы читаемый аккаунт назывался в самом доказательстве, —
без него вывод PDA для одного аккаунта глушит сырое чтение другого. Спека задала ресивер как
**ведущий** идентификатор выражения. Для любого Anchor-чтения это `ctx`, и условие вырождалось
в «в теле есть хоть какое-то сравнение, где упомянут ctx». На этом
`candy-machine/…/set_collection_during_mint.rs:116` был заглушен сравнением
`ctx.accounts.metadata.data_len() == 0` — проверкой **другого** аккаунта, то есть ровно той
«декоративной проверкой», о которой спека предупреждает в разделе VL005. Лечится взятием
**последнего** сегмента-идентификатора; S3, которому нужна квалифицированная форма, оставлен как
был. Второй круг заодно сделал видимым `assert!(pda == account.key)` — токены макроса не
разбираются в `Expr::Binary`, и до этого такая проверка не доказывала ничего.

Итог: **8 → 44 → 32 → 31**. VL001 4, VL003 579, VL004 66, VL005 21 — не изменились ни на одном
дереве.

| anchor-check | 1 | 2 |
| program-examples | 7 | 6 |
| metaplex-program-library | 0 | 9 |
| marginfi-v2 | 0 | 8 |

находка VL002 на строке 15; строка возвращена.

## Отбор файлов: тесты, бенчи и фаззинг не сканируются

Первое изменение, которое трогает не правило, а сам обход дерева, — и потому единственное,
которое двигает числа сразу всех пяти правил.

Инструмент сканировал всякий `.rs` под целевым деревом. Заметная часть находок приходилась на
код, который никогда не исполняется on-chain: модули `#[cfg(test)]`, интеграционные тесты Cargo
и харнессы `cargo fuzz`. Фаззер, который десериализует сырые данные аккаунта без проверки
владельца, делает ровно свою работу; сообщать об этом как об уязвимости — шум.

**Очевидная реализация неверна, и это проверено, а не предположено.** Отбросить всякий путь,
в котором встречается компонент `tests` или `fuzz`, нельзя: в репозитории самого Anchor весь
корпус примеров лежит под верхнеуровневым `tests/`, каждый пример — отдельный крейт с
собственным `Cargo.toml`, и в одном из них
(`tests/auction-house/programs/auction-house/src/lib.rs:1098`) находится **единственное
подтверждённое истинное срабатывание VL001 на всём корпусе** — тот самый `CreateAuctionHouse`,
на котором правило калибровалось. Фильтр по имени каталога удаляет его. Ровно так же обманывает
имя файла: `controller/amm/tests.rs` в drift — действительно тестовый модуль, а
`test-utils/src/test.rs` в marginfi — обычный библиотечный код.

Поэтому все четыре механизма (`src/scope.rs`) опираются на **объявление**, а не на имя:

- **M1 — интеграционные тесты и бенчи Cargo.** Ищем ближайший вверх по дереву каталог с
  `Cargo.toml` — это корень крейта; файл тестовый, если путь относительно этого корня начинается
  с `tests` или `benches`. Это определение самого Cargo, и именно «ближайший», а не «корневой»,
  спасает случай Anchor: для файла примера ближайший манифест — манифест самой программы,
  относительно которого путь начинается с `src`.
- **M2 — крейты `cargo fuzz`.** В `Cargo.toml` крейта есть `package.metadata.cargo-fuzz = true` —
  ключ, который пишет туда сам `cargo fuzz init`. Оба фаззера корпуса (marginfi, openbook-v2)
  его несут.
- **M3 — файлы, объявленные как `#[cfg(test)] mod NAME;`.** Атрибут стоит на **месте
  объявления**, а не в самом файле, поэтому `tests.rs` о своей тестовости ничего не знает.
  Собираем объявления при разборе и разрешаем их в `NAME.rs` или `NAME/mod.rs` по правилам
  модулей Rust: для `foo/bar.rs` подмодули лежат в `foo/bar/`, и только для `lib.rs`, `mod.rs`
  и `main.rs` — рядом. Проверено на всех 20 файлах корпуса с именем `tests.rs`/`test.rs`:
  разрешение объявления даёт верный ответ на всех 20, совпадение по имени — на 19 из 20,
  причём ошибка в опасную сторону.
- **M4 — встроенные блоки `#[cfg(test)] mod NAME { … }`.** Находка, чья строка попала в диапазон
  блока, отбрасывается. Диапазон берётся из span'ов AST, а не подсчётом скобок.

M1–M3 отсекают файл до разбора, M4 работает после — его информация существует только в AST.
Распознаватель `cfg(test)` один на M3 и M4: принимает `#[cfg(test)]` и `#[cfg(all(test, …))]`,
отвергает `#[cfg(feature = "test")]` и `#[cfg(not(test))]`.

Все места, где ошибка проглатывается (`Cargo.toml` не читается, файл не парсится), дают ответ
«не тестовый», то есть файл всё-таки сканируется. Направление верное: возможное ложное
срабатывание, а не пропущенная уязвимость.

Молчать о выброшенном нельзя, поэтому заголовок прогона сообщает число пропущенных файлов —
и только когда оно ненулевое: `→ analyzing 241 Rust files (Anchor 1.0.2) (64 test files skipped) …`

Замер на двенадцати деревьях, 326 пропущенных файлов, 209 снятых находок:

| правило | было | стало |
|---|---|---|
| VL001 | 4 | **4 — не изменилось. Это и есть страховка.** |
| VL002 | 31 | 24 |
| VL003 | 579 | 382 |
| VL004 | 66 | 61 |
| VL005 | 21 | 21 |

VL001, оставшееся ровно четвёркой вместе с находкой в auction-house, — главный результат замера,
а не побочный: он и означает, что ни один механизм не залез в настоящий on-chain код. Основной
объём снятого — VL003, и почти весь он приходится на M3 (169 находок в файлах `tests.rs` drift и
mango).

## Публичный API библиотеки

Крейт публикуется на crates.io, поэтому всё `pub` — это обязательство по semver. Номер версии
нельзя переиздать: каждый публичный элемент в 0.1.0 — это обязательство, от которого нельзя
отступить, не подняв мажорную версию.

**Поддерживаемая публичная поверхность 0.1.0:** функция `scan()`, возвращающая `ScanReport`;
типы `Finding` и `Severity`, читаемые из него; рендереры в `report`. Всё остальное — внутреннее.

- **Модуль `anchor` — `pub(crate)`.** `AnchorModel`, `AccountsStruct`, `AccountField`,
  `AccountTy` и `Constraint` недоступны снаружи крейта. Модель строится под конкретный набор
  правил и будет меняться по мере их расширения.
- **Модуль `rules` — `pub(crate)`.** `RuleContext`, `Rule` и `LinkedRule` недоступны снаружи
  крейта. Создание сторонних правил в 0.1.0 намеренно не является поддерживаемой возможностью.
- Типы `syn` и `proc-macro2` не торчат в публичных сигнатурах. Это закрытый риск: ранее выход
  `syn 3` стал бы ломающим изменением vaultlint, даже если сам vaultlint не менялся. Сейчас оба
  крейта используются только в `pub(crate)`-модулях, и это проверено компиляцией внешнего крейта
  против vaultlint: ни `syn`, ни `proc-macro2` не утекают в публичные сигнатуры.
- `ScanOptions`, `ScanReport`, `Finding`, `SkippedFile` помечены `#[non_exhaustive]`: они точно
  будут расти (выбор правил, exclude-маски, per-file `overflow-checks`), и добавление поля не
  должно ломать мажорную версию. `ScanOptions::new(root)` — единственный способ создать
  `ScanOptions` снаружи крейта, поскольку `#[non_exhaustive]` запрещает struct-literal
  конструирование во внешнем коде.
- `Finding` и `Severity` умеют не только `Serialize`, но и `Deserialize` — иначе потребитель не
  может прочитать собственный JSON vaultlint его же типами.
- `Severity` реализует `Display` (строки `"low"` / `"medium"` / `"high"`, те же, что у `serde`)
  и `FromStr` с тем же набором строк — пара образует полный round-trip. Метод `label()`, дающий
  форму `LOW`/`MED`/`HIGH` для терминального вывода, — `pub(crate)`: две конкурирующие публичные
  текстовые репрезентации одного типа — ловушка для потребителей.
- Публичные рендереры (`report::render`, `report::human::render`, `report::json::render`,
  `report::sarif::render`) возвращают `std::io::Result<()>`, а не `anyhow::Result<()>`: так в
  API не проникает сторонний тип ошибок. Ошибки `serde_json` при записи JSON конвертируются через
  `std::io::Error::from` — эта конверсия принципиальна: `serde_json::Error::source()` возвращает
  `None`, и без неё обрыв пайпа (`vaultlint scan . | head`) не опознаётся как broken pipe и
  завершается кодом выхода 2 вместо 0.

## Страницы правил на сайте

`docs_url` каждой находки ведёт на `https://vaultlint.com/rules/<VL00N>` — этот же адрес уходит
в JSON и в SARIF как `helpUri`, то есть становится ссылкой «подробнее» в GitHub Security.
Публиковать инструмент, у которого все ссылки в находках ведут на 404, нельзя: это первое, на
что кликает читатель.

Пять страниц правил — обязательное условие публикации, наравне с исправлением кода. Требования
к ним описаны отдельной инструкцией в `docs/rule-pages.md` (в проекте vaultlint.com, вне репозитория кода).

## Риски

- **Ложные срабатывания — риск номер один.** Инструмент, который кричит на здоровый код, удаляют
  в тот же день. Отсюда узкие правила, канарейка в тестах, механизм подавления и мягкий `--fail-on`.
- **`syn` не даёт семантики.** VL002–VL005 намеренно локальны — в пределах файла, функции или
  структуры. VL001 — единственное исключение: он смотрит в тело хендлера на один вызов вглубь
  через индекс использований, потому что без этого сужение до реальной формы бага невозможно.
  Глубже одного вызова анализ не идёт и в перспективе относится к платному LLM-слою.
- **~~Мажорный релиз `syn` ломает vaultlint.~~** _(Закрыто в R8.)_ До R8 типы `syn` и
  `proc-macro2` присутствовали в публичных сигнатурах, и выход `syn 3` был бы ломающим
  изменением semver для vaultlint, даже если сам vaultlint не менялся. Закрыто переводом всех
  модулей, использующих эти типы, в `pub(crate)`: модули `anchor`, `rules`, `parse`, `scope` и
  остальные внутренние модули недоступны снаружи крейта. Проверено компиляцией внешнего крейта
  против vaultlint: ни `syn`, ни `proc-macro2` не появляются в публичных сигнатурах.
- **Объём работы.** Детерминированный движок — это недели фокуса, а не выходные. Срезы нужны
  именно для того, чтобы каждая неделя заканчивалась рабочим инструментом.
